# 1. Architecture and file map

## 1.1 The three layers

```
             application
                  │  XML_Parse / XML_ParseBuffer / XML_GetBuffer / handlers
                  ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ xmlparse.c  — PARSER                                                 │
 │   XML_ParserStruct, processors, input buffer, DTD tables, tag stack, │
 │   namespaces, entity expansion, accounting, public API               │
 │                                                                      │
 │      ┌───────────────────────────┐                                   │
 │      │ xmlrole.c — PROLOG ROLES  │  XmlTokenRole(state, tok, ...)    │
 │      │ grammar state machine     │◄──── prolog/DTD tokens only       │
 │      └───────────────────────────┘                                   │
 └───────────────┬──────────────────────────────────────────────────────┘
                 │  XmlContentTok / XmlPrologTok / XmlAttributeValueTok /
                 │  XmlConvert / XmlGetAttributes / XmlUpdatePosition ...
                 ▼
 ┌──────────────────────────────────────────────────────────────────────┐
 │ xmltok.c (+ xmltok_impl.c, xmltok_ns.c) — TOKENIZER                  │
 │   ENCODING vtables for UTF-8, UTF-16LE/BE, Latin-1, ASCII, unknown;  │
 │   byte classification tables; transcoding to UTF-8/UTF-16            │
 └──────────────────────────────────────────────────────────────────────┘
```

Responsibilities are split cleanly:

* The **tokenizer is stateless and never allocates.** Each scanner gets
  `(enc, ptr, end, &nextTokPtr)` and returns a token code. On success it sets
  `*nextTokPtr` to the end of the token. All "where am I" state lives in the
  caller. Because of this the parser can call a scanner again on the same
  bytes after more input arrives. That is how incremental parsing works.
* The **role layer** holds a tiny amount of state (a `PROLOG_STATE` with a
  handler function pointer plus a few counters). It knows the DTD grammar but
  nothing about storage or callbacks.
* The **parser** does everything with side effects: allocation, hash tables,
  string interning, callbacks, error reporting, entity expansion, and
  security limits.

Only three translation units are compiled: `xmlparse.c`, `xmltok.c`, and
`xmlrole.c` (see `expat/lib/Makefile.am`). `xmltok_impl.c` and `xmltok_ns.c`
are `#include`d into `xmltok.c`, several times each, as templates.

## 1.3 Build-time configuration

Expat is heavily configured by preprocessor macros. Most come from
`expat_config.h`, which CMake or autotools generate. The ones that change
the architecture:

| Macro | Default | Effect |
|-------|---------|--------|
| `XML_DTD` | on | Parameter entities, external subset, conditional sections (`<![INCLUDE[`/`<![IGNORE[`), `XML_SetParamEntityParsing`, `XML_UseForeignDTD`. Adds `XML_IGNORE_SECTION_STATE` to the tokenizer and several processors and roles. Requires `XML_GE=1`. |
| `XML_GE` | 1 | General entity expansion. **Also gates all the amplification accounting and the allocation tracker.** With `XML_GE=0`, internal entity values are not expanded: the declared value is replaced by the literal text `&amp;name;` (`storeSelfEntityValue`), so the application sees `&name;`. The check at `xmlparse.c:75` makes it a compile error to leave `XML_GE` undefined. |
| `XML_NS` | on | Namespace support. Builds a second, `_ns` copy of every encoding in which `:` is `BT_COLON` (in the non-NS copies it is just `BT_NMSTRT`). Namespace *processing* is still opt-in at run time through `XML_ParserCreateNS`. |
| `XML_CONTEXT_BYTES` | 1024 | How many already-parsed bytes `XML_GetBuffer` keeps before `m_bufferPtr`, so that `XML_GetInputContext` can show context around errors. `0` turns this off and enables a zero-copy fast path in `XML_Parse`. |
| `XML_UNICODE` / `XML_UNICODE_WCHAR_T` | off | Makes `XML_Char` a 16-bit unit (UTF-16) instead of UTF-8 `char`. Inside `xmlparse.c` this changes `ICHAR`, `XmlConvert`, `XmlEncode`, `MUST_CONVERT`, and the internal encoding (`xmlparse.c:166-200`). |
| `XML_ATTR_INFO` | off | Keeps byte offsets for every attribute name and value (`XML_GetAttributeInfo`). Adds `m_attInfo`. |
| `XML_LARGE_SIZE` | off | Makes `XML_Index`/`XML_Size` 64-bit on platforms where `long` is 32-bit. |
| `XML_MIN_SIZE` | off | Smaller but slower tokenizer: byte classification goes through function pointers (`STANDARD_VTABLE`) instead of inline table lookups, and only one copy of the template code is needed. |
| `XML_TESTING` | off (on for `libtestpat`) | Exposes some internals to the test suite (`expat_malloc`, `g_bytesScanned`, a writable `g_reparseDeferralEnabledDefault`). |
| `HAVE_GETRANDOM`, `HAVE_ARC4RANDOM_BUF`, `XML_DEV_URANDOM`, … | detected | Sources of entropy for the hash salt. Without any of them the build fails with an `#error` unless `XML_POOR_ENTROPY` is defined (`xmlparse.c:148`). |
| `BYTEORDER` | detected | Picks the UTF-16 internal encoding variant at compile time (`xmltok_ns.c`). |

## 1.4 Design idioms you will see everywhere

### Preprocessor templates instead of runtime branching

The tokenizer is the hot path. Instead of writing one scanner that branches on
"is this UTF-16?" for every byte, Expat writes each scanner once in
`xmltok_impl.c` against an abstract macro interface. It then includes that file
three times from `xmltok.c` with different definitions:

```c
#define PREFIX(ident) normal_##ident     // 1-byte encodings: UTF-8, Latin-1, ASCII
#define MINBPC(enc) 1
#define BYTE_TYPE(enc, p) SB_BYTE_TYPE(enc, p)   // table lookup type[(unsigned char)*p]
#include "xmltok_impl.c"

#define PREFIX(ident) little2_##ident    // UTF-16LE
#define MINBPC(enc) 2
#define BYTE_TYPE(enc, p) LITTLE2_BYTE_TYPE(enc, p)
#include "xmltok_impl.c"

#define PREFIX(ident) big2_##ident       // UTF-16BE
...
```

`xmltok_ns.c` uses the same trick with `NS(x)` / `ns(x)` to produce both
`XmlInitEncoding` and `XmlInitEncodingNS`. The byte-type tables use it too:
`asciitab.h` is literally a list of 128 `BT_*` initializers, included inside a
`{ ... }` array initializer. `#define BT_COLON BT_NMSTRT` is put around the
include to make the non-namespace variant.

### Vtables in C

`struct encoding` (`xmltok.h:172`) is a vtable: `scanners[XML_N_STATES]`,
`literalScanners[2]`, plus `nameLength`, `getAtts`, `utf8Convert`, and so on.
The parser calls only through macros like `XmlContentTok(enc, …)`, which
expand to `enc->scanners[XML_CONTENT_STATE](enc, …)`. Changing encoding in
the middle of a document (after a BOM or an `encoding="…"` declaration) just
swaps the `ENCODING *`.

`PROLOG_STATE` (`xmlrole.h:112`) uses the same pattern with a single
`handler` pointer that changes itself as the grammar advances. So does the
parser's `m_processor`.

### "C++ in C" member naming

Every field of `struct XML_ParserStruct` has an `m_` prefix and every function
takes `XML_Parser parser` as its first argument, like an implicit `this`.
Comments in `XML_ExternalEntityParserCreate` (`xmlparse.c:1834`) still
mention "magical uses of the preprocessor to make field access look more like
C++". Those macros are gone; access is now explicit `parser->m_…`.

### Calling-convention macros

`FASTCALL`, `PTRCALL`, and `PTRFASTCALL` (`internal.h`) mark internal
functions and function pointers. They used to select `regparm(3)` on i386
GCC. On every other platform they expand to nothing.

### Portable string constants

String literals that must be `XML_Char` are spelled out as arrays of
`ASCII_*` constants (for example `implicitContext[]` at `xmlparse.c:1026` and
the `xmlNamespace[]` in `addBinding`). This keeps them correct in UTF-16 builds
and on EBCDIC hosts, because `ASCII_x` is the numeric code point, not the
host's `'x'`.

### Defensive coding style

* `/* LCOV_EXCL_LINE */` marks branches believed unreachable that are kept
  as safety nets. Many come with a long comment explaining why they are
  thought to be unreachable.
* Before nearly every multiplication or addition that feeds an allocation
  there is a check such as `if (x > INT_MAX - y) return XML_ERROR_NO_MEMORY;`.
  These are often wrapped in `#if UINT_MAX >= SIZE_MAX` to keep
  `-Wtype-limits` quiet on 64-bit targets.
* Algorithms that used to recurse on input-controlled depth (content model
  building, internal entity expansion) are now iterative. See
  [07](07-memory-and-security.md).
